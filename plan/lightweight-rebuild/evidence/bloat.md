# bloat: Bloat forensics: how the incumbent LitHarness grew, why pruning failed, and guardrails that keep a rebuild small

The whole repository is 47 days old: 1,194 commits between 2026-08-12 and 2026-09-27, with a peak of 142 commits on 08-22. Measured with `git diff --shortstat <empty-tree> <sha>`:
- src grew from 5,964 lines (08-13) to 65,891 at HEAD 40f58a2.
- tests/*.py grew from 3,815 to 96,265 lines.
- research/*.py grew from 0 to 100,618 lines.
- The stage-0 ledger grew from 18 entries (431 lines) to 267 entries (27,439 lines, 2.0 MB).

src levelled off after 09-08 (+4.4k lines in 20 days), but tests (+20.8k) and research code (+35.3k) kept growing. Late growth was verification and research, not product.

Main causes, in order:
1. Each operator read or finding became a subsystem, a ledger entry and a test module. Read 8 alone produced about 45k lines in two days.
2. The "alive" test for code was whether anything cited it, and the ledger and docs cite almost everything. The pruning track found 2 of 101 scripts dead. Its rules refused to delete refuted research arms.
3. Tests check documentation and the ledger. They stop deletions and cost 9% of suite time.
4. The persistence and layering apparatus: 31 port protocols, a 2,549-line store, 39 migrations, 52 tables, a 7,033-line CLI and a second 2,059-line composition root.
5. The verification regime: an 85% coverage floor, 1,051 asserts on literal prompt text, five check lanes, a leak audit over the whole git history, and one sustained job at a time on the shared box.
6. Parallel-session overhead: 162 merges, 33 local and 25 remote branches, and ledger-number collisions.

The only large cut (530f40e, driven by the operator's "must stay lean") removed 34% of src. It had fully grown back 5.2 days later, because nothing enforced a size limit. The earlier clean-start prototype (09-08) ran alongside the main pipeline and was retired the next day.

Guardrails must be tiny and hard, with no allowlists:
- one short line-budget test
- a whole-suite time limit
- no database until a continuity test fails without one
- a new component is admitted only with a failing case from a real chapter
- a capped decision file that is rewritten, not appended
- no tests that read docs
- experiments kept outside the runtime and the test suite

Every process guard the incumbent built became code of its own, with its own tests.

## Risks
- The rebuild grows back at the incumbent's rate: about 25 commits a day at a median of 156 lines, reaching 40k lines in about a week. => Put the budget test in the first commit. Raising any limit is its own commit with a reason. The planner should require each increment to state the net change in lines.
- The guardrails turn into bloat themselves: an allowlist dict on the budget test, a survey script, a governance doc with a checker. => A hard rule that each guardrail is at most about 25 lines, with no exception mechanism and no tests of the guardrail. If a guard needs an exception, change the number or delete the guard.
- Failing regression cases pile up into a judge harness or fixture corpus, the incumbent's measurement programme under a new name. => Cap the regression fixtures (for example at most 20 text cases). Checks are plain asserts, or a recorded read kept under experiments/. No model-judge framework inside the runtime.
- Other sessions' work is lost or merged in mid-wipe. At this snapshot there are 13 modified files and about 974 untracked .py lines, and 33 local branches. => Before the wipe, take the box/session lock, commit or explicitly discard in-flight work with operator sign-off, tag the archive, and push. Wipe on a single branch with one writer.
- A time limit on the suite is flaky on Windows CI, where run times vary about threefold per the ci.yml comment. => Enforce the limit locally with a generous margin, or run CI on Linux only with a single job. Treat the limit as a size signal, not a precise benchmark.
- Wiping the repo breaks references from stored books, runs/ receipts and Lite's baseline traces into the incumbent code and ledger. => Use an annotated archive tag and keep runs/ and books outside the new tree. The new tree's README points to the tag.
- Evidence for the rebuild is thin: one brief, one pair, a model judge from the same family (REPORT.md:18-19,135-139). The rebuild may regress on continuity the incumbent handled. => Keep the incumbent tagged and runnable for long-serial comparisons, as the report recommends. Add continuity only through failing cases.
